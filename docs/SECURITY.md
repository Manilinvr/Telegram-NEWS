# Модель безопасности

## Доступ

Система приватная. Регистрации нет: единственная учётная запись создаётся
скриптом `bootstrap:admin`, маршрут регистрации в API отсутствует. Все
данные, кроме проверки живости (`/api/health`), требуют входа.

## Пароли

Хранятся в виде хэша scrypt с индивидуальной солью. Параметры стоимости
записаны внутри строки хэша, поэтому их можно ужесточить позже, не ломая
существующие пароли.

Требование к паролю — длина не менее 12 символов. Ставка сделана на длину,
а не на обязательный набор спецсимволов: длинная фраза надёжнее и не
провоцирует записывать пароль. Распространённая последовательность
отклоняется только тогда, когда составляет основную часть пароля — простая
проверка «содержит» забраковала бы нормальную длинную фразу.

## Защита от перечисления учётных записей

Несуществующий адрес и неверный пароль дают **одинаковый** ответ. При
отсутствии пользователя всё равно выполняется фиктивная проверка пароля:
иначе учётную запись выдало бы время ответа.

## Защита от перебора

- Блокировка учётной записи после `AUTH_MAX_FAILED_ATTEMPTS` неудач на
  `AUTH_LOCKOUT_MINUTES`. Блокировка включается ровно на пороге и не
  продлевается бесконечно от каждой последующей попытки.
- Отдельный жёсткий лимит частоты запросов на `/api/auth/login`.
- Дополнительный отказ при большом числе неудач с одного адреса —
  до проверки пароля.
- Все попытки входа фиксируются.

## Сессии

- В cookie уходит только случайный идентификатор (256 бит энтропии);
  в БД хранится его SHA-256. Утечка дампа базы не даёт угнать сессию.
- Cookie сессии — `httpOnly`: недоступна скриптам, что ограничивает
  последствия XSS.
- `Secure` обязателен в production (проверяется при старте).
- `SameSite=Lax` по умолчанию.
- Ограничение общего срока жизни и отдельный таймаут простоя.
- Смена пароля отзывает **все** сессии, включая текущую.

## CSRF

Отдельный токен привязан к конкретной сессии. Он лежит в доступной скриптам
cookie и возвращается заголовком `x-csrf-token`. Сессия живёт в cookie,
поэтому браузер отправит её и при запросе с чужого сайта, но токен из
заголовка чужой сайт прочитать не может. Сравнение — за постоянное время.
Проверка обязательна для всех изменяющих методов.

## Инъекции

Все значения передаются параметрами запроса; строка SQL не собирается
конкатенацией пользовательских данных. Защита обеспечивается построением, а
не экранированием. В наборе тестов есть попытка выполнить `DROP TABLE` через
поле поиска — таблица остаётся на месте.

## Заголовки

`helmet` с политикой CSP, `frame-ancestors 'none'`, `nosniff`, ограничение
`Referrer-Policy` и `Permissions-Policy`, HSTS в production.

## Загрузка и отдача файлов

- Ограничение размера (`MEDIA_MAX_FILE_MB`) и белый список типов.
- Размер проверяется потоково: сервер может не прислать `content-length`.
- Ключи объектов защищены от выхода за пределы каталога хранения.
- Хранилище **не публично**. Локальные файлы отдаются по подписанной
  ссылке с ограниченным сроком; S3 — по presigned URL. Знание пути к файлу
  без подписи доступа не даёт.
- Отдача с `nosniff` и `Content-Disposition: inline`.

## Журнал аудита

Действия администратора записываются в `audit_logs`. Записи **неизменяемы
на уровне БД**: триггер запрещает `UPDATE` и `DELETE`. Журнал должен быть
доказательством, а не редактируемой таблицей.

## Секреты

- Не хранятся в коде, репозитории, README и SQL.
- Берутся из окружения; `.env` исключён из Git.
- В production отсутствие или недостаточная длина `SESSION_SECRET` и
  `CSRF_SECRET` — фатальная ошибка старта, а не тихий переход на небезопасное
  значение по умолчанию.
- Логи вырезают токены и ключи: даже при случайном логировании объекта
  конфигурации значение не попадёт в лог.
- Пароль первичного администратора показывается один раз и нигде не
  сохраняется в открытом виде.

## Права

Публикация доступна ролям `OWNER` и `ADMIN`, удаление источников — только
`OWNER`. Проверка выполняется на сервере для **каждого** действия:
интерфейс может быть любым, доверять ему нельзя.

Критичные настройки требуют повторного ввода пароля: сессия могла остаться
открытой на чужом устройстве.

## Что рекомендуется дополнительно

- Развёртывание за HTTPS-прокси; `TRUST_PROXY=true` только за доверенным
  прокси, иначе клиент подменит свой адрес и обойдёт лимит частоты.
- Ограничение доступа к панели по IP или через VPN.
- Регулярные резервные копии (см. [BACKUP.md](BACKUP.md)).
- Отдельные учётные данные БД с минимально необходимыми правами.
