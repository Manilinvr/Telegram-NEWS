# Запуск сайта: от нуля до рабочей панели

Инструкция доводит до работающего адреса, на котором открывается панель
мониторинга, а не текст README.

---

## Почему сейчас виден README

Сейчас сайт обслуживается GitHub Pages. Это **статический** хостинг: он
умеет отдавать готовые файлы и рендерить README, но не умеет запускать
программы. Этой системе нужны:

- процесс Node.js (API, сбор новостей, обработка);
- база PostgreSQL;
- фоновый воркер.

Ничего из этого GitHub Pages не предоставляет, поэтому он показывает
единственное, что понимает, — README.

**Вывод:** нужен хостинг, умеющий запускать Node.js. База у вас уже есть —
Supabase.

---

## Что понадобится

| Что | Состояние | Стоимость |
|---|---|---|
| База PostgreSQL | Supabase уже подключён | бесплатный тариф подходит |
| Хостинг для Node.js | нужно выбрать | бесплатный/минимальный тариф |
| Ключ AI | **не обязателен** | можно начать без него |
| Токены Telegram/VK | не обязательны на старте | — |

Система запускается и работает без единого внешнего ключа: разбор будет
выполняться правилами. Ключи добавляются позже, без переустановки.

# Часть 1. База данных

## Шаг 1.1. Применить миграции

Файлы уже подготовлены в каталоге `supabase/migrations/`. **Не берите файлы
из `packages/backend/src/db/migrations/`** — там есть секции отката, и
SQL-редактор Supabase выполнит их тоже, удалив только что созданные
таблицы. Именно поэтому появлялась ошибка «relation … does not exist».

Выберите один способ.

### Способ А. Через интеграцию Supabase с GitHub (у вас уже подключена)

1. Убедитесь, что в настройках интеграции указана ветка
   `claude/wonderful-faraday-rpn9q6` — либо влейте её в ту ветку, которая
   там указана.
2. Отправьте изменения в эту ветку.
3. Supabase применит миграции сам и запишет их в
   `supabase_migrations.schema_migrations`.

### Способ Б. Через SQL-редактор вручную

Откройте **SQL Editor** в Supabase и выполните файлы из
`supabase/migrations/` **по одному, строго по порядку имён**:

```
20260101000001_extensions.sql
20260101000002_auth.sql
20260101000003_sources.sql
20260101000004_events.sql
20260101000005_editorial.sql
20260101000006_ops.sql
20260101000007_search.sql
20260101000008_hardening.sql
```

Если появится диалог про Row Level Security — нажмите **Run without RLS**.
RLS включает сама миграция `008_hardening`, а автоматическое включение
средствами Supabase создало бы политики, открывающие доступ.

### Способ В. С вашего компьютера

```bash
DATABASE_URL="<строка подключения>" DATABASE_SSL=true npm run migrate
```

## Шаг 1.2. Проверить результат

В SQL-редакторе Supabase:

```sql
select count(*) as tables from pg_tables where schemaname = 'public';
-- ожидается 20 (или 21, если миграции применял раннер проекта)

select count(*) filter (where rowsecurity) as with_rls,
       count(*) as total
from pg_tables where schemaname = 'public';
-- with_rls должно равняться total

select count(*) as policies from pg_policies where schemaname = 'public';
-- ожидается 0 — это и есть запрет доступа извне
```

Если таблиц 0 — миграции не применились. Если меньше 20 — часть файлов
пропущена, примените недостающие по порядку.

## Шаг 1.3. Взять строку подключения

Supabase → **Project Settings → Database → Connection string**.

Возьмите **Session pooler** (порт 5432) или прямое подключение.
**Transaction pooler** (порт 6543) не подходит: очередь задач удерживает
транзакции, и этот режим отклоняет параметры, которые приложение задаёт
при подключении.

Строка выглядит так:

```
postgresql://postgres.abcdefgh:ВАШ_ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
```

Сохраните её — она понадобится на следующем шаге. Это секрет: не
коммитьте и никому не пересылайте.

# Часть 2. Запуск приложения

Приложение собрано так, что **один процесс отдаёт и панель, и API** — один
адрес, никаких настроек CORS. Воркер тоже можно запустить внутри этого же
процесса.

Ниже — Railway как самый быстрый путь. Подойдёт любой хостинг, умеющий
запускать Node.js: Render, Fly.io, обычный VPS.

## Шаг 2.1. Создать сервис

1. Зайдите на <https://railway.app>, войдите через GitHub.
2. **New Project → Deploy from GitHub repo**.
3. Выберите `Manilinvr/Telegram-NEWS`.
4. В настройках сервиса укажите ветку
   `claude/wonderful-faraday-rpn9q6`.

Railway обнаружит Node.js и Dockerfile. Можно использовать любой вариант;
с Dockerfile сборка воспроизводимее и в образ входит ffmpeg, нужный для
работы с видео.

## Шаг 2.2. Команды сборки и запуска

Если хостинг спрашивает команды (без Dockerfile):

```
Build command:  npm ci && npm run build
Start command:  node packages/backend/dist/server.js
```

## Шаг 2.3. Переменные окружения

Сгенерируйте два секрета **на своём компьютере**:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Добавьте переменные в настройках сервиса:

```bash
NODE_ENV=production

# База — строка из шага 1.3
DATABASE_URL=postgresql://postgres.xxx:ПАРОЛЬ@aws-0-...pooler.supabase.com:5432/postgres
DATABASE_SSL=true

# Секреты из команд выше — по одному в каждую переменную
SESSION_SECRET=<первое сгенерированное значение>
CSRF_SECRET=<второе сгенерированное значение>

# Обязательно в production: cookie только по HTTPS
COOKIE_SECURE=true
# Только если хостинг работает за своим прокси (Railway, Render — да)
TRUST_PROXY=true

# Схемой управляет Supabase — раннер при старте отключаем.
# Если применяли миграции способом В, поставьте true.
MIGRATE_ON_STARTUP=false

# Воркер внутри процесса API: для личной установки достаточно
RUN_WORKER_IN_API=true

# Создать владельца при первом запуске
BOOTSTRAP_ON_STARTUP=true
BOOTSTRAP_ADMIN_EMAIL=efimenkodaniil151@gmail.ru
BOOTSTRAP_ADMIN_PASSWORD=<придумайте пароль, не короче 12 символов>

# Пока без внешних ключей — разбор выполняется правилами
AI_PROVIDER=mock
EMBEDDING_PROVIDER=local
TELEGRAM_INGEST_MODE=none
TRANSCRIPTION_PROVIDER=none
STORAGE_DRIVER=local

# Защита от случайной публикации, пока всё не проверено
TELEGRAM_PUBLISH_DRY_RUN=true
```

Порт задаётся хостингом автоматически; при необходимости укажите
`API_PORT` тем значением, которое требует платформа.

## Шаг 2.4. Дождаться развёртывания

В логах должно появиться:

```
Интерфейс отдаётся этим же процессом
Воркер запущен внутри процесса API
Учётная запись владельца «...» создана
API запущен
```

Откройте выданный адрес — должна появиться форма входа, а не README.

## Шаг 2.5. Постоянное хранилище для медиа (если нужно)

При `STORAGE_DRIVER=local` файлы лежат в каталоге контейнера и **исчезают
при каждом пересоздании**. Для постоянного хранения либо смонтируйте том в
`/app/storage`, либо переключитесь на S3-совместимое хранилище:

```
STORAGE_DRIVER=s3
S3_ENDPOINT=https://<ваш-эндпоинт>
S3_BUCKET=nnm-media
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
```

# Часть 3. Первый вход

1. Откройте адрес сервиса.
2. Введите email и пароль из `BOOTSTRAP_ADMIN_PASSWORD`.
3. Зайдите в **Настройки → Безопасность** и смените пароль.
4. **Удалите `BOOTSTRAP_ADMIN_PASSWORD` из переменных окружения** — учётная
   запись уже создана, и хранить пароль там больше незачем.

Панель будет пустой: источники ещё не подключены. Это нормально.

# Часть 4. Подключение источников

## Telegram

Самый быстрый способ, не требующий токенов, — публичный предпросмотр:

```
TELEGRAM_INGEST_MODE=public-preview
```

Затем **Источники → Добавить**, укажите `@username` канала.

Ограничение: каналы, отключившие предпросмотр, читаться не будут — система
сообщит об этом при добавлении. Для своих каналов лучше режим `bot`,
подробности в [SETUP-SOURCES.md](SETUP-SOURCES.md).

## VK

Нужен сервисный ключ доступа приложения VK:

```
VK_ACCESS_TOKEN=vk1.a....
```

Затем добавьте сообщество, указав его короткое имя.

Источник проверяется на доступность **до** сохранения — недоступный
добавлен не будет, и вы сразу увидите причину.

# Часть 5. Качественные черновики (по желанию)

Пока `AI_PROVIDER=mock`, система работает, но заголовки и формулировки
делаются правилами: эвристика отбирает предложения исходного текста, а не

Для полноценного разбора:

```

```

Учтите: тексты новостей при этом уходят внешнему сервису.

# Часть 6. Публикация в Telegram

Пока `TELEGRAM_PUBLISH_DRY_RUN=true`, материал проходит **весь** путь —
проверки, одобрение, финальный контроль лексики — но в канал ничего не
отправляется. Это защита от случайной публикации при настройке.

Когда всё проверено:

1. Создайте бота у [@BotFather](https://t.me/BotFather).
2. Добавьте его администратором канала с правом публикации.
3. Задайте переменные:
   ```
   TELEGRAM_PUBLISH_BOT_TOKEN=123456:AA...
   TELEGRAM_PUBLISH_CHANNEL=@ваш_канал
   TELEGRAM_PUBLISH_DRY_RUN=false
   ```

# Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| Виден README | Открыт адрес GitHub Pages, а не хостинга приложения |
| `relation ... does not exist` | Миграции не применены или взяты не из `supabase/migrations/` |
| `SESSION_SECRET обязателен в production` | Не задан или короче 32 символов |
| `COOKIE_SECURE обязан быть true` | Добавьте `COOKIE_SECURE=true` |
| Сервис падает при старте, таблицы уже есть | Поставьте `MIGRATE_ON_STARTUP=false` |
| Не удаётся подключиться к базе | Используется transaction pooler (6543) — возьмите session pooler (5432) |
| Вход не запоминается | Нет `COOKIE_SECURE=true` при HTTPS либо не задан `TRUST_PROXY=true` |
| «Слишком много запросов» | Сработала защита от перебора: подождите минуту |
| Панель пустая | Источники не добавлены либо ещё не прошёл первый опрос |
| Публикации есть, событий нет | Дайте воркеру минуту; проверьте **Аналитика → Очередь задач** |
| Медиа пропали после обновления | `STORAGE_DRIVER=local` без постоянного тома — см. шаг 2.5 |

## Где смотреть диагностику

- **Аналитика** — ошибки обработки и очередь задач.
- **Источники** — состояние каждого канала и причина сбоя.
- **Настройки → Общие** — какая конфигурация реально применена.
- **Настройки → Журнал действий** — что происходило в системе.

# Локальный запуск (для проверки перед развёртыванием)

```bash
npm install
cp .env.example .env
# впишите DATABASE_URL и два секрета

npm run migrate
npm run seed
npm run bootstrap:admin     # пароль покажется один раз

# демо-данные, чтобы увидеть систему в работе
npm run seed:demo -w @nnm/backend

npm run dev
```

Панель откроется на <http://localhost:5173>.
